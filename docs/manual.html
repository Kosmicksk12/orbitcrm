1 · Panorama general

Qué es. Danivo CRM es una aplicación web para gestionar un taller de reparación de celulares y electrónica: órdenes de servicio en un tablero, inventario de repuestos, ventas de accesorios, gastos, clientes (ficha automática), garantías con enlace público, y —en la capa "vendible como SaaS"— prueba gratis, cobro y un panel para el dueño del producto.

Backend / datos
Supabase — Postgres + Auth + Storage. La seguridad la impone Row Level Security (RLS) en la base, no el código.
Hosting

PWA
Instalable; el service worker offline quedó desactivado (ver §5 y §6).

Cómo funciona el aislamiento entre talleres

Cada usuario pertenece a exactamente un taller (shops), con rol admin o member. Todas las tablas de datos tienen una columna shop_id y políticas RLS que solo dejan ver/editar filas del propio taller. Un usuario nunca ve datos de otro taller. El "super-admin" (dueño del SaaS) sí ve todo, pero solo a través de funciones especiales que chequean is_platform_admin().

3 · Cómo publicar y trabajar en el proyecto

Publicación (autorizada automática, ver CLAUDE.md)

El flujo para cada cambio es verificar → commit → push a main → deploy. Antes de cada push:

  1. npx tsc --noEmit — debe salir limpio.
  2. npx next lint — debe salir limpio.
  3. npx next build — debe compilar sin errores. Nunca correr next build con next dev activo — corrompe la carpeta .next.
  4. Si algo falla, NO publicar. Arreglar primero.
  5. Solo si los tres pasan: git add, git commit, git push origin main, npx vercel --prod.
  6. Después del deploy, verificar rápido en https://orbitcrm-blond.vercel.app que no haya errores.

Correr en local

npm install
npm run dev            # http://localhost:3000  (desarrollo, con hot reload)
npm run build && npm start   # simula producción (más fiel)

Aviso: next dev a veces no muestra componentes nuevos aunque el código esté bien (artefacto del hot reload). Si algo nuevo "no aparece" pero tsc y next build pasan, probá contra npm run build && npm start antes de asumir que hay un bug.

Migraciones de base de datos

El código nunca ejecuta SQL de esquema. El flujo es: escribir el archivo en supabase/migration-*.sql, abrir el SQL Editor de Supabase, pegar el contenido y darle "Run" a mano. Los archivos .sql quedan en el repo solo como respaldo y referencia.

Cómo funciona RLS (el modelo de seguridad)

  • user_shop_ids() — función que devuelve el/los shop_id del usuario actual. Casi toda política dice shop_id in (select public.user_shop_ids()).
  • is_shop_admin(shop_id) — true si el usuario es admin de ese taller. Las políticas de DELETE suelen exigirlo.
  • is_platform_admin() — true si el usuario está en platform_admins. Lo chequean las funciones del panel /admin.
  • Los SELECT casi siempre son abiertos para miembros del taller; INSERT/UPDATE también; DELETE solo admins.

5 · Funcionalidades — qué hace cada una, sus archivos y sus riesgos

5.1 Papelera (soft delete) de órdenes y gastos

Qué hace. "Eliminar" no borra: marca la fila con deleted_at y la saca de las vistas normales. Desde la papelera se puede restaurar o "borrar para siempre" (solo admins).

Archivos. components/orders/OrdersTrashModal.tsx, components/expenses/ExpensesTrashModal.tsx; el filtro .is("deleted_at", null) está en todas las lecturas (Panel, Clientes, buscador, cierre de mes, notificaciones, garantía).

Riesgos. Si en el futuro se agrega una lectura de órdenes o gastos sin el filtro .is("deleted_at", null), van a aparecer filas de la papelera donde no deberían. Ventas no tiene papelera a propósito (ahí "eliminar" repone stock y mezclar eso con restaurar es delicado).

5.2 Historial de WhatsApp

Qué hace. Cada vez que se abre WhatsApp desde la app (lista de órdenes, tarjeta kanban, comprobante de garantía) se registra el mensaje prellenado en whatsapp_messages. Se ve en el modal de la orden y en la ficha de cliente (agrupado por teléfono).

Archivos. components/orders/WhatsAppLink.tsx (registra al hacer clic), components/orders/WhatsAppHistory.tsx (lista), lib/whatsapp.ts. Tabla whatsapp_messages.

Riesgos. El registro es "fire and forget": si falla no muestra error. Y solo registra que se abrió WhatsApp, no que el cliente lo haya recibido o leído — el texto de la UI lo aclara, pero conviene no venderlo como "mensajes enviados".

5.3 Fotos del equipo (Supabase Storage)

Qué hace. Evidencia del estado del equipo al recibirlo. Se pueden adjuntar al crear la orden (quedan en memoria y se suben después del insert, con el order_id nuevo) o al editarla. Se ven en el modal y en la garantía interna; nunca en la garantía pública. Máx. 12 fotos por orden; se comprimen en el navegador antes de subir.

Archivos. components/orders/OrderPhotos.tsx, lib/orderPhotos.ts. Bucket privado order-photos, ruta {shop_id}/{order_id}/{uuid}. Tabla order_photos. Las miniaturas usan URLs firmadas (el bucket es privado).

Riesgos. (1) Las policies de storage.objects filtran por el primer segmento de la ruta (shop_id): si algún código sube con una ruta distinta, la subida se rechaza — es la parte más delicada de seguridad. (2) Borrar una orden "para siempre" limpia los archivos de Storage (deleteAllOrderPhotoFiles en el trash modal); si esa llamada falla quedan archivos huérfanos (costo menor, no seguridad). (3) Las URLs firmadas vencen (1 h) — si alguien deja el modal abierto mucho rato, las miniaturas dejan de cargar hasta recargar.

5.4 Landing pública + páginas legales

Qué hace. / muestra una landing de marketing para visitantes sin sesión. /terminos y /privacidad son borradores con marcadores [TU NEGOCIO], [FECHA], etc.

Archivos. components/marketing/LandingPage.tsx, components/marketing/LegalDoc.tsx, app/page.tsx, app/terminos/page.tsx, app/privacidad/page.tsx. El middleware.ts deja /terminos y /privacidad como rutas públicas.

Riesgos. Los legales tienen que completarse con datos reales antes de cobrarle a nadie — hoy son plantillas. Los precios de la landing son presentacionales (todos los botones van a /login).

5.5 Prueba de 15 días → modo solo-lectura

Qué hace. Un taller nuevo arranca con 15 días de acceso total (subscription_status = 'trialing', trial_ends_at = now() + 15 días). Al vencer, si no hay suscripción activa, pasa a solo lectura: pueden entrar y ver todo, pero no crear/editar/borrar. Los talleres existentes quedaron en active por la migración.

Archivos. lib/subscription.ts (la lógica: resolveAccess() → writable/inTrial/expired), components/shop/ShopContext.tsx (expone readOnly), hooks/useWriteGuard.ts, components/layout/TrialBanner.tsx, components/settings/SubscriptionSettings.tsx. El bloqueo está aplicado en órdenes, ventas, gastos, inventario, productos solicitados, fotos y gestión de equipo.

Riesgos importantes. El bloqueo solo-lectura es solo del lado del cliente (deshabilita botones y corta los handlers). No hay RLS que lo respalde todavía: un usuario técnico con la prueba vencida podría, en teoría, escribir llamando a la API de Supabase directo. Es un hueco conocido y aceptable por ahora (no hay clientes externos con prueba vencida). Se cierra cuando se conecte Stripe (ver §6 y §7). El ShopProvider hace fail open: si la columna no existe o la consulta falla, el taller se trata como active — para no bloquear a nadie por un error.

5.6 Panel de super-admin (/admin)

Qué hace. Para el dueño del SaaS: ver todos los talleres con su estado de prueba/suscripción, contadores (miembros, órdenes, ventas), correo del dueño y última actividad; y cambiar el estado de un taller a mano (activar / extender prueba 15 días / marcar vencida).

Archivos. app/admin/layout.tsx, app/admin/page.tsx (chequea platform_admins; si no, notFound() → 404), components/admin/AdminDashboard.tsx. Usa los RPC admin_list_shops y admin_set_shop_subscription. El link "Panel de administración" aparece en el menú de usuario solo si sos platform admin (el (dashboard)/layout.tsx lo pasa a Topbar).

Riesgos. Para agregar otro super-admin hay que insertar una fila en platform_admins a mano en Supabase (no hay UI). El panel confía en que los RPC hacen el chequeo de autorización — si alguien crea un RPC nuevo para el panel, tiene que empezar con if not public.is_platform_admin() then raise exception ....

5.7 Guía de primeros pasos (onboarding)

Qué hace. Un taller nuevo ve una tarjeta "Primeros pasos" en el Panel con checklist (nombre del taller, primera orden, primer producto, invitar equipo). Desaparece sola cuando los 3 pasos obligatorios están hechos, o con "Ocultar" (se guarda en localStorage del dispositivo).

Archivos. components/dashboard/OnboardingChecklist.tsx; app/(dashboard)/dashboard/page.tsx calcula el progreso de datos que ya consulta.

Riesgos. "Ocultar" es por-dispositivo (no por-cuenta). El check "nombre del taller" mira profiles.shop_name o shops.name — se simplifica cuando se unifique el nombre (§6).

5.8 Rediseño de marca

Qué hace. El logo pasó de la elipse tipo "ojo" a una "D" geométrica blanca sobre el cuadrado azul #2647E0. Wordmark unificado: Space Grotesk 700 con letter-spacing -0.03em en toda la app.

Archivos. components/ui/Logo.tsx (un solo <svg>), los <span> del wordmark en Sidebar/Topbar/login/landing/legales/admin, design/icon-source.svg + design/icon-maskable-source.svg, scripts/gen-brand-icons.mjs (regenera favicon.ico y los PNG de public/icons/), public/manifest.webmanifest.

Riesgos. (1) Los PNG de public/icons/ van con caché de un año (immutable): para cambiarlos de nuevo hay que renombrarlos (por eso llevan sufijo -r2) y actualizar el manifest + app/layout.tsx. La constante REV en el script controla ese sufijo. (2) Dispositivos con la PWA ya instalada: el ícono de la pantalla de inicio no cambia hasta reinstalar la PWA (en iOS es obligatorio). (3) Las pantallas de arranque public/splash/* todavía tienen la marca vieja (§6).

5.9 Endurecimiento del middleware (fix del error 504)

Qué hace. El middleware.ts llamaba a supabase.auth.getUser() en cada request sin límite de tiempo propio; una demora de Supabase se convertía en 504 MIDDLEWARE_INVOCATION_TIMEOUT de Vercel. Ahora: (1) Promise.race con timeout de 2,5 s — si no responde, el request pasa sin redirigir (los layouts del área privada igual chequean la sesión al renderizar); (2) se saltea Supabase del todo para rutas que no lo necesitan (/, legales, /garantia/*, assets).

Riesgos. Si el timeout salta, ese request no refresca la cookie de sesión (se refresca en el siguiente) y un usuario logueado que caiga en /login justo en ese momento ve el login en vez de rebotar al dashboard. Es raro y aceptable.

5.10 Service worker desactivado

Qué pasó. Tras un cambio de versión del SW + reinstalación de la PWA, el service worker quedaba "envenenado" y servía /offline.html en bucle, dejando la app sin cargar aunque el servidor respondiera. Se desactivó: public/sw.js ahora se autodesregistra, borra todas las cachés y recarga las pestañas; components/pwa/ServiceWorkerRegister.tsx solo desregistra SW viejos.

Consecuencia. Se perdió el modo offline. Si se quiere de vuelta, hay que reintroducir un SW con estrategia robusta: nombres de assets versionados, skipWaiting automático, y que un 404 de un chunk no deje una página rota cacheada.

8 · Cómo leer el código — patrones que se repiten

Server Component vs Client Component

Por defecto los archivos de app/ son server components: corren en el servidor, pueden usar await y consultar Supabase con lib/supabase/server.ts. Un archivo que empieza con "use client" corre en el navegador: puede usar useState, useEffect, eventos, y consulta con lib/supabase/client.ts. El Panel (dashboard/page.tsx) es server; casi todo lo demás interactivo es un "PageClient".

El patrón "PageClient"

"use client";
export function OrdersBoard() {
  const supabase = createClient();
  const { shopId, isAdmin } = useShop();
  const { readOnly } = useWriteGuard();
  const { toast } = useToast();
  const [orders, setOrders] = useState([]);

  async function load() {                    // consulta y llena el estado
    const { data } = await supabase.from("service_orders")
      .select("*").is("deleted_at", null).order("created_at", { ascending: false });
    setOrders(data ?? []);
  }
  useEffect(() => { load(); }, []);

  async function handleSubmit(values) {      // los handlers escriben y vuelven a load()
    if (readOnly) return;                    // guard de solo-lectura
    await supabase.from("service_orders").insert({ ...values, shop_id: shopId });
    load();
  }
}

Cosas que se repiten

  • Plata en centavos. Las columnas terminan en _cents y son enteros. Para mostrar: formatCurrency(cents) de lib/utils.ts.
  • Soft delete. Toda lectura de órdenes/gastos lleva .is("deleted_at", null).
  • Contexto del taller. const { shopId, role, isAdmin, readOnly, access, subscription } = useShop() — disponible en cualquier componente dentro de (dashboard).
  • Bloqueo de escritura. const { readOnly } = useWriteGuard(); los handlers empiezan con if (readOnly) return; y los botones llevan disabled={readOnly}.
  • Modales. <Modal> para formularios; <ConfirmDialog> para confirmar acciones destructivas (nunca window.confirm).
  • Avisos. const { toast } = useToast(); toast({ title, description, variant }) — variantes: "default", "success", "danger".
  • Íconos. Componentes SVG en components/ui/Icons.tsx: <IconWrench width={16} height={16} />.
  • Tailwind. Las clases usan tokens: bg-surface, text-ink, border-line, text-accent, y su par dark:. Definidos en tailwind.config.ts.
  • Tipos. lib/types.ts tiene la interfaz de cada entidad (ServiceOrder, Sale, Expense, InventoryProduct, WhatsAppMessage, OrderPhoto, ...).

Para agregar una funcionalidad nueva típica

  1. Si necesita tabla nueva: escribir supabase/migration-*.sql con la tabla, sus índices y las policies RLS (copiar el patrón de migration-requested-products.sql: SELECT/INSERT/UPDATE para miembros, DELETE para admins). Correrla a mano en Supabase.
  2. Agregar la interfaz TypeScript en lib/types.ts.
  3. Crear el/los componentes en components/<dominio>/ siguiendo el patrón PageClient.
  4. Si escribe datos, cortar con useWriteGuard() y deshabilitar los botones con readOnly.
  5. npx tsc --noEmit + npx next lint + npx next build → commit → push → npx vercel --prod.
